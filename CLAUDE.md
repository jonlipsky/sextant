# CLAUDE.md

Sextant is a Roslyn-based semantic code indexer for .NET projects. It extracts symbols, references, call graphs, and relationships into SQLite and exposes them via MCP for AI agents.

## Build & Test

```bash
dotnet build Sextant.slnx
dotnet test Sextant.slnx --no-build
dotnet test --no-build --filter "FullyQualifiedName~SomeTest"
```

**Subprocesses in the benchmark harness and its tests go through `tests/Shared/BoundedProcess.cs` (issue #144).**
Link that file for new test subprocess code. It drains stdout+stderr concurrently, closes stdin, bounds the wait (on
timeout it kills only the process tree it started — never processes by name), and never waits on pipe EOF after the
child exits (a descendant that inherited the pipes — a reused MSBuild node, a compiler server, a leaked grandchild —
can hold them open indefinitely). `BoundedProcess.DotnetRestore` runs `dotnet restore --disable-build-servers
-nodeReuse:false` with `MSBUILDDISABLENODEREUSE=1`/`DOTNET_CLI_USE_MSBUILD_SERVER=0`. Never read a redirected child's
streams sequentially to EOF or call the parameterless `WaitForExit()` on it (the older call sites in other test
projects and `src/` are tracked in #146). CI's `Build & Test` job has a 30-minute timeout and runs `dotnet test` with
`--blame-hang-timeout 10m` (hang dumps + blame sequence files are uploaded as the `test-hang-diagnostics` artifact).

## Project Structure

```
Sextant.Core        — models, project identity, configuration
  ← Sextant.Store   — SQLite storage, migrations, queries
    ← Sextant.Indexer — Roslyn workspace loading, symbol extraction
      ← Sextant.Daemon — file watcher, incremental indexing
    ← Sextant.Mcp   — MCP server, tool implementations (Store + Core)
Sextant.Service      — standalone index-service data plane (Core + Store + Indexer + Mcp)
  ← Sextant.Service.Host — ASP.NET Core host (control/query HTTP + HTTP MCP)
Sextant.Cli          — CLI entry point (Daemon + Indexer + Mcp + Service.Host)
```

**Dependencies point OUTWARD from core.** `Sextant.Service` references `.Core`/`.Store`/`.Indexer`/`.Mcp`
(its service-only MCP tools `list_repositories`/`search_symbols` and `GrantReadAuthorizer` build on `.Mcp`); `Sextant.Service.Host`
references only `.Service` (it reaches `.Mcp` transitively); `Sextant.Cli` references `.Daemon`/`.Indexer`/
`.Mcp`/`.Service.Host`. The core libraries (`.Core`/`.Store`/`.Indexer`/`.Daemon`/`.Mcp`) must **never**
reference the service or ProcessStack (`ArchitectureBoundaryTests` asserts this).

**Nothing in this repo references ProcessStack.** ProcessStack reaches Sextant only through the service's
generic HTTP APIs (a delegate token plus a signed caller assertion, grants, the control plane). No project
may reference a `ProcessStack.*` package, and no `apps/processstack/` tree or `psapp.yaml` may come back
(`ArchitectureBoundaryTests`). Service code uses generic names (caller, assertion, tenant, delegate), never
ProcessStack types; the ProcessStack-flavoured defaults (the `CALLER_HEADER` name `X-ProcessStack-Caller`
and the `CALLER_IDPS` value `processstack`) are configurable.

**Specs:** in-flight initiative specs live in `specs/<YYYYMMDD>-<kebab-name>/`; `docs/` remains the durable
reference.

## Critical Rules

- **MSBuildLocator.RegisterDefaults()** must be called before any Roslyn type loads (first call in `Program.cs`).
- **Roslyn symbols must be semantic.** Use `ISymbol.ToDisplayString(SymbolDisplayFormat.FullyQualifiedFormat)` for the display FQN.
- **Symbol identity is `symbol_key`, not the FQN.** Build every key through the one canonical factory (`SemanticSymbolKeyFactory`) — a Roslyn documentation ID when available, else a version-scoped `src:`/`meta:` fallback. The display FQN is query/display data and is no longer unique (overloads share it). Uniqueness is `(project_id, symbol_key)`. Exclude anonymous/tuple artifacts from top-level symbols. Resolve FQN lookups via `SymbolResolver`, which reports ambiguity instead of silently picking a row.
- **SQLite only, no ORMs.** Raw parameterized SQL via `Microsoft.Data.Sqlite`. WAL mode.
- **Indexing writes go through a bounded, batched unit-of-work.** Open one `IndexWriteSession` (via `IndexDatabase.BeginWriteSession`) per index run; it drives explicit `BEGIN IMMEDIATE`/`COMMIT`/`ROLLBACK` on the single writer connection (do **not** use `SqliteConnection.BeginTransaction()` — raw statements keep the connection's ambient transaction so existing store commands enrol automatically). Commit at document/project batch boundaries (`CommitBatch()`); `RowsWritten()` triggers a safety-net commit at `BatchRowThreshold`. Never wrap an unbounded monorepo in one transaction. Reuse prepared insert commands (`store.CreateInsertCommand()` + `Insert(cmd, …)`) inside a batch instead of one command per row.
- **Atomic generation publish via the `index_runs` ledger.** Each run stages under a generation id (`IndexRunStore.BeginScope` → `IndexRunState.Staging`) and is published by flipping the last-complete pointer **inside the final write transaction** (`IndexRunStore.MarkComplete`, guarded on `status = staging`), so a reader of `GetLastCompleteRun` sees the previous complete generation or the new one, never a "complete" pointer without its committed data. Per-project/per-file replacement is an atomic delete+insert within one batch. Phase 3 does **not** physically isolate generation rows, so a concurrent reader querying the shared symbol/reference tables mid-run can still observe a partially rebuilt (hybrid) generation and a crashed run leaves earlier committed batches in place — full cross-generation reader isolation (never observing a hybrid) is Phase 9 (immutable snapshots). On dispose without completion the scope abandons the run; `IndexDatabase.Recover()` (run at writer startup) checkpoints a valid WAL and sweeps abandoned/stale staging generations. Assumes a **single writer** (enforced by one writer connection + `BEGIN IMMEDIATE`); recovery has no cross-process lease, so do not run two indexers against one DB.
- **Bounded WAL.** Writer sets `wal_autocheckpoint` + `journal_size_limit` from `IndexWriteOptions`; the run ends with an explicit `PRAGMA wal_checkpoint(TRUNCATE)`. Never let the WAL grow to tens-of-times the final DB — measure peak WAL/SHM/staged with the Phase 1 harness. Caveat: `wal_autocheckpoint` is a trigger, not a hard cap, and a long-lived concurrent reader pins the WAL and defers truncation, so the bound holds under the normal short-reader workload.
- **Full and incremental indexing share ONE contribution model and must converge on the same canonical DB.** `IndexOrchestrator.IndexSolutionAsync` takes an optional `projectCanonicalFilter` (null = full; a set = incremental). Registration + dependency phases always run for every loaded project (idempotent); the symbol/relationship/reference/comment/call-graph/api-surface phases skip any project not in the filter. `IncrementalIndexer` computes the **undirected dependency closure** (`ProjectClosure`) of the affected projects and delegates to the orchestrator with that filter, so incremental runs the *literally identical* extraction code over a narrowed set — never a divergent second path. Replacement is delete-by-owner-project-version (`store.DeleteByProject`, TFM-scoped) then insert the fresh batch atomically inside the Phase 3 write session. Do **not** delete references/call-graph rows per source file (that would drop cross-project inbound occurrences owned by other files) — rely on the owning project's `DeleteByProject` cascade.
- **Document-oriented extractor (Phase 5) is the default (`document_extractor`, default ON; legacy retained as an emergency fallback).** When ON, the legacy declaration-driven relationship/reference/call-graph phases are replaced by ONE `extracting_occurrences` phase: `DocumentSemanticExtractor.ExtractDocument` walks each processed project's documents **once** over a single cached semantic model + root, emitting references/calls/relationships attributed to the nearest enclosing source symbol (**usage-site** ownership). `IOperation` drives calls/object-creation/access-kind; name-syntax binding covers type/member mentions (no operation); malformed binds bump a completeness diagnostic. Resolve every target through the shared `SemanticSymbolKeyFactory` + Phase-2 `SymbolCatalog` (built BEFORE occurrences); reduce to original definition, reduced-extension→static original, constructor→constructed type. **Compilation-scoped exact target identity:** the extractor carries each reference/call target's real owning project (bound `ISymbol.ContainingAssembly` → `Solution.GetProject(IAssemblySymbol)` → per-TFM project id, mapped in the orchestrator; extractor stays DB-free via a `Func<IAssemblySymbol,long?>` delegate), so a target whose declaration key exists in several projects (multi-TFM dependency, `extern alias`) binds the **exact** bound TFM's row via `SymbolCatalog.TryResolveExact` (never counts `AmbiguousEdgeBindings`). `TryResolveEdge` (lowest-id pick + ambiguity count) is only the fallback for out-of-solution/metadata targets. Relationship edges still use the shared key path (parity with legacy; making them exact is a tracked follow-up). **Critical Phase-4 reconciliation:** references still persist `in_project_id`=using project and `symbol_id`=**target** declaration, and every cross-project call/inheritance also emits a reference, so `ReferenceStore.GetCrossProjectPairs` + the undirected closure stay complete — the target-cascade deletion domain equals the usage-site production domain, so **no** closure/deletion change is needed. Dedup per (per-TFM) project via `DocumentContributionSet` before persistence: reference `(target,file,line,kind,access)`, call `(caller,callee,file,line)`, relationship `(from,to,kind)`. Keep the legacy path (`ReferenceExtractor`/`CallGraphBuilder`/`RelationshipExtractor.ExtractInstantiates` + `FindReferencesAsync`) reachable behind the flag as an emergency fallback; `ExtractorParityTests` is the differential gate (relationships identical, calls a superset, no spurious type targets, no `override` reference kind).
- **Per-document extraction is parallelized behind a bounded, deterministic pipeline (Phase 6), but the writer stays single-threaded.** When the document extractor is ON, the `extracting_occurrences` phase runs through `ParallelExtractionPipeline.RunAsync`: a producer materializes projects **one at a time in solution order** (so only ~1 compilation is live → bounded memory), extracts each project's documents in parallel (`Parallel.ForEachAsync`, capped at `ExtractionParallelismOptions.MaxParallelism`), merges the per-document `DocumentContributionSet`s by **ascending document ordinal** (`MergeFrom`), and hands each project's merged set to a bounded `System.Threading.Channels` channel; a **single consumer** (`PersistProject`) drains it in enqueue order and is the ONLY stage that resolves targets, reads/mutates the `SymbolCatalog` (incl. `AmbiguousEdgeBindings`), and touches the writer. **Never move catalog resolution or SQLite work onto the parallel workers.** Workers must not share a `SemanticModel` (each builds its own per document); the `ResolveTargetProject` memo is a `ConcurrentDictionary` keyed by `SymbolEqualityComparer.Default` (its factory — `solution.GetProject` + read-only `projectRoslynToId` — is side-effect-free, so benign races are safe). **Determinism is the hard invariant:** persistence order = (project ordinal, document ordinal, intra-document emission order), independent of task completion, so the canonical index is byte-for-byte identical to a single-threaded run — `ParallelDeterminismTests` (P=1 vs P=8) and `ExtractorParityTests` are the gates. Cancellation/worker-failure tear down cleanly with no writer deadlock (linked CTS; producer always completes the channel; a consumer fault cancels the token to release a producer parked on a full channel) and the run scope abandons the staging generation — never marks it complete. Tunables: `max_parallelism`/`SEXTANT_MAX_PARALLELISM` (0=auto `min(cores,8)`, positive clamped to core count) and `extraction_queue_capacity`/`SEXTANT_EXTRACTION_QUEUE_CAPACITY`. No schema/migration change (scheduling only).
- **`file_index` is populated during initial (full) indexing, not just incrementally.** The symbol phase seeds one `file_index` row per indexed document with a content hash, and `SetEvaluationFingerprint` records the per-project evaluation fingerprint (`EvaluationFingerprint.Compute` over the project file + `Directory.Build.*`/`global.json`/package-assets/analyzer-config inputs). Daemon restart compares those fingerprints: unchanged file **and** unchanged project evaluation ⇒ no semantic reindex is scheduled; a changed source hash, a changed evaluation fingerprint, or a create/delete/rename escalates only the affected dependency closure.
- **Historical `api_surface` snapshots are self-contained and survive a working-index rebuild.** `api_surface_snapshots` carries its own `symbol_key`/`fqn`/`accessibility` and a nullable `symbol_id` with `ON DELETE SET NULL`, so deleting/replacing live symbols during a rebuild never cascade-deletes a committed commit snapshot (migration `009`).
- **Source identity stored once; occurrences are compact (Phase 7).** A source path lives **once** in `files.repo_relative_path` (repo-relative, never absolute) with a versioned `file_versions` row whose `content_hash` is a **raw SHA-256 BLOB**. `symbols` reference a `file_version_id` (not a `file_path`) and store `kind`/`accessibility` as **integer** ordinals. The separate `references` and `call_graph` tables are unified into ONE `occurrences` table: `(in_project_id, target_symbol_id, source_symbol_id?, file_version_id, line, col, kind, flags)`. A **pure reference** has `source_symbol_id IS NULL` (byte-for-byte the old `references` rows); a **call edge** additionally sets `source_symbol_id` = the enclosing caller (the old `call_graph` row). `argument_flow`/`return_flow` reference an `occurrence_id`. Kinds/flags are integer enums/bitflags (occurrence `flags` bits 0–1 = access: none/read/write/read-write; bit 2 = candidate, `ReferenceStore.CandidateFlag`); hashes are BLOBs, not hex. `ReferenceStore`/`CallGraphStore`/`FileStore` are thin adapters over these tables so MCP queries keep working. **Closure/cascade preserved:** `ReferenceStore.GetCrossProjectPairs` selects source-NULL occurrences whose `in_project_id != symbols.project_id` (feeds `ProjectClosure`); the target FK still cascades on the referenced declaration and reset = `symbolStore.DeleteByProject` + `fileStore.DeleteByProject`. **Snippets are not stored** — `SourceContextRetriever` reproduces context at query time only when the local file's hash matches `file_versions.content_hash` (else location without snippet).
- **Rebuild gate (Phase 7 / criterion 6).** Migration `011` is rebuild-required and runs `DELETE FROM index_runs`, so an upgraded-but-not-reindexed DB is not mistaken for a complete generation. `IndexDatabase.CheckReadiness()` returns an actionable message for an older schema (rebuild), a newer schema (upgrade Sextant), or a current-schema DB with no complete generation **and** no symbols (run a full index) — surfaced by the CLI query handler, `serve`, and the `get_index_status` MCP tool. `LatestSchemaVersion` = 11.
- **Project identity is `(git_remote_url, repo_relative_path, target_framework)`.** Never disk paths. Each evaluated target framework of a multi-targeted project is a distinct logical project. Because `DeleteByProject` is TFM-scoped, replacing one TFM's project row (full or incremental) never touches another TFM's symbols — each per-TFM `project_id` is replaced independently.
- **Generated code excluded:** `IsImplicitlyDeclared`, `*.g.cs`, `*.designer.cs`, `obj/`.
- **MCP tool responses include `meta` object:** `queried_at`, `index_freshness`, `result_count` (plus `ambiguous`/`candidates` when one symbol key is declared in several project versions).
- **Symbol arguments resolve through ONE query-time resolver, and failures are loud (issues #149/#163).** Every symbol-taking tool calls `SymbolResolver.Lookup` (`SymbolQuery` parses `Ns.Type`, optional `global::`, `Type.Member`, a parameter list in C# keywords or framework names, or a documentation ID); stored data is unchanged (a member's container and parameters come from its documentation-ID key), so it needs no re-index. Ranking: exact key > earlier reading > full path > suffix > bare name (a container-less row such as a type parameter gets no full-path credit for a bare name) > fewer generic segments named without their arity (`Result` prefers `Result` over `Result<T>`, so printed names round-trip) > case > fewer generic-only parameter matches > (no `kind` asked) type over member over type parameter. The parser refuses input over `SymbolQuery.MaxLength` (2048) and nesting over `SymbolTypeTerm.MaxNestingDepth` (32) as `invalid_argument`, so its recursion is bounded. When a name matches more rows than the name lookup reads (2000), types of that name are read on their own too, so the cap never hides a type. Several DIFFERENT keys tying for best is `Ambiguous`: a tool that needs one symbol returns the `ambiguous_symbol` error with candidates, never an arbitrary pick (`find_symbol`, a search, lists them instead); the same key in several projects stays `Resolved` with the `SymbolAmbiguity` meta. Not-found returns `symbol_not_found` with ≤5 near misses (`meta.candidates`), named by `SymbolNamer` in a form the tools accept back; every `fully_qualified_name` a tool prints goes through `SymbolNamer` too. A structured error (`ResponseBuilder.BuildError`/`BuildSymbolError`, i.e. `meta.error`) becomes an MCP tool error (`isError: true`) through `ToolErrorResults.CallToolFilter`, registered innermost on both the service `/mcp` and stdio. Bad `project_id`/`scope`/`kind`/namespace arguments are `invalid_argument`, never an unfiltered read. A valid but empty answer is NOT an error and says so in the top-level `message`. Cross-repository usages resolve the provider symbol with the same resolver restricted to the provider's pinned projects (`SymbolStore.ProjectRestriction`), so a name never unions several provider symbols' usages; its not-found carries no candidates. Lookups seek `ix_symbols_project_name_nocase`/`ix_symbols_key`, so cost follows same-named symbols, not index size. A member's output `signature` is `symbols.declaration` (migration `026`: `SymbolExtractor.DeclarationFormat`, return type + modifiers + parameter names + defaults), falling back to the legacy `symbols.signature` for a pre-026 row; never overwrite the legacy column, because `SymbolNamer` prints member FQNs from it, and `find_by_signature` parses the shown text with `SignatureText`.
- **MCP server reads SQLite directly** — does not depend on daemon running.
- **JSON serialization uses `SnakeCaseLower` naming policy.**
- **FTS5 for text search** — `symbols_fts` virtual table over `symbols(display_name, doc_comment)`, kept in sync via SQL triggers. The per-row triggers are **not** the WAL driver once writes are batched (measured: peak WAL stays ~1× the final DB with triggers active).
- **Standalone index service (Phase 13) is an additive DATA PLANE, never required for local operation.** The service lives in NEW projects (`Sextant.Service` / `Sextant.Service.Host`) that depend on the core libs — the core libs stay ProcessStack-AGNOSTIC (Phase 14 orchestrates OVER this service's APIs; do not invert). It owns the durable Phase-9 snapshot catalog + semantic store on a **single writer connection** serialized by an async gate, guarded by a **cross-process single-writer lease** (`writer_lease`, issue #38) acquired **fail-closed** at `Start` (migrate → lease → recover → reconcile, so recovery never abandons a live writer's staging generation). `SnapshotService.EnsureSnapshotAsync` is **idempotent** via the Phase-9 `SnapshotIdentity.Hash`: `snapshot_jobs.identity_hash` is UNIQUE, so repeated ensures attach to ONE durable job (criterion 1) and the worker runs once. A worker claiming `complete`/`partial` but publishing no complete snapshot is **downgraded to `failed`** (and its `snapshot_id` nulled). Structured per-project diagnostics live in `snapshot_job_diagnostics` (criterion 5). **The local stdio MCP path + standalone local indexing MUST remain FULLY functional with ZERO service dependency (criterion 6).**
- **Service HTTP surface SEPARATES control from query planes** (`Sextant.Service.Host/ServiceApp.cs`): `/health`=service AVAILABILITY (open), `/ready`=worker CAPACITY (503 when a query-only node has no worker), `/control/*`=ensure/status/resolve/retention (control token), `/mcp`+`/query/*`=HTTP MCP + snapshot paging (query token). A null query token = anonymous read (dev); the service refuses to START without a control token unless `INSECURE_OPEN_CONTROL_PLANE` explicitly opens it (SX-6d). **Query reads use a connection independent of the writer** (WAL concurrent readers) so queries never block a running index. **Wire format is snake_case** (`ServiceJson.Options`): responses pass `ServiceJson.Options` explicitly AND request-body binding is configured via `Http.Json.JsonOptions` to `SnakeCaseLower`+`WhenWritingNull` so inbound snake_case binds.
- **The service `/mcp` always honors the `X-Sextant-Repository` selector, and can require it (SVC-1).** `ServiceApp` wires the header into `DatabaseProvider.RequestedRepository` whether or not `READ_POLICY` is set. The generic `DatabaseProvider.RequireRepositorySelection` hook (default `() => false`, so the local stdio/CLI path is byte-identical) makes `TryBeginRead` fail with `repository_required` when no selector is present. It runs FIRST, before readiness and authorization, so the error depends only on the request and names no repository. The service composes the requirement in `ServiceApp.RepositorySelectionRequirement` (today only `ServiceOptions.RequireRepositorySelection`; further per-request reasons join with `||`). A NAMED repository with no complete default-branch snapshot resolves to `DenyAll` (`FederatedReadContext.SelectionUnresolved`) and NEVER widens to the LegacyPinned/Unscoped fallback: it gets an actionable `repository_not_found` tool error on a permissive path and the uniform not-found under an enforcing authorizer. The uniform not-found (`ResponseBuilder.BuildNotFound`) is ONE `repository_not_found` tool error with a fixed message, identical for a forbidden, absent, branch-less or unprovisioned read (Phase 17 forbids a DISTINCT denial code, not a shared one); it is an error so an agent never reads a denial as "no matches". With the requirement off, a no-header read keeps today's unselected default (Unscoped across every repository of a multi-repository catalog).
- **Per-call selection travels in reserved tool args on the service `/mcp` only (SVC-2).** `ToolSelectionFilters` (Service.Host) registers MCP SDK request filters on the stateless `/mcp`, and the stdio server registers none, so its `tools/list` stays byte-identical.
  - **`tools/list`:** each repository-scoped tool (`ServiceApp.RepositoryScopedTools`) gets optional string `repository`/`branch` in a CLONED `Tool`. Never mutate the SDK's shared definitions. A name the tool already declares is kept and not reserved (none of the eight remote tools declares one today).
  - **`tools/call`:** the filter strips the reserved args before binding, and canonicalizes `repository` with `RepositoryUrlPolicy` (full URL, `host/owner/repo`, or `owner/repo` on the one explicit host). The argument beats the header; a canonical mismatch is `selector_conflict`, and a non-string or policy-refused value is `invalid_selector`.
  - **Where the selection lives:** the result is stored as `ToolCallSelection` in `HttpContext.Items`, one JSON-RPC message per stateless POST. The `DatabaseProvider` accessors read it, and later caller and grant checks reuse it.
  - **Branch:** the generic `DatabaseProvider.RequestedBranch` (default null) pins `SnapshotStore.GetSelectedSnapshotRowForRepositoryBranch`. A branch with no repository is `repository_required` in `TryBeginRead` regardless of the requirement, and a branch miss is the `SelectionUnresolved` DenyAll.
  - **Fail closed:** a scoped call the SDK did not match fails closed. Never change the call's target tool, because that re-runs SDK authorization.
- **Worker scratch is quarantined from persistent volumes (criterion 3).** `ServicePaths` asserts the scratch root is NOT nested with the checkout/artifact/cache volumes and `ReleaseScratch` refuses any path outside the scratch root, so scratch cleanup can never delete published data (extends Phase-8 servable guard + Phase-9 `BranchPointerProtection`).
- **Service-owned retention/GC (issues #46/#37/#54) runs under the writer lease.** `RetentionService` computes a **protected set** — pending snapshots, snapshots on non-deletable/servable generations, branch-pointed snapshots — transitively expanded across `base_snapshot_id` + `snapshot_dependencies` (consumer→provider) to a fixpoint, and only then GCs orphaned snapshot DATA rows (#46, bounded) and prunes orphan source blobs (#37, bounded + protected-set-aware). The protected set includes providers referenced by ANY RETAINED consumer generation, not just branch-pointed heads (#54), coupled with the Phase-12 published-status gate.
- **Remote snapshot federation (issue #51):** `GET /query/snapshots/{identityHash}/symbols` serves immutable cursor-paged snapshot pages; `RemoteHttpBaseSnapshotSource` is the Phase-11 base-snapshot-source client — **cache-first** (`SnapshotPageCache` bounded LRU keyed by `{identityHash}:{cursor}:{limit}` = caching-by-snapshot-id + transparent offline fallback to a cached base), per-request **timeout** (linked CTS), and 401/403/timeout/connection-failure → `RemoteSnapshotUnavailableException`.
- **Live MCP federation (issue #60):** the base-snapshot seam (`IBaseSnapshotSource` + page DTOs + `LocalBaseSnapshotSource`/`RemoteHttpBaseSnapshotSource`/`SnapshotPageCache`/`CompositeBaseSnapshotSource`) lives in **`Sextant.Store`** (moved out of `Sextant.Service`) so BOTH the standalone service AND the live MCP query planner reference it without inverting the `Sextant.Service`→`Sextant.Mcp` dependency. The composition root (`McpServerSetup`) builds a `RemoteBaseSnapshotFederation` from config (`peers`/`SEXTANT_PEERS`, `remote_fetch_timeout_seconds`/`SEXTANT_REMOTE_FETCH_TIMEOUT`, `peer_query_token`/`SEXTANT_PEER_QUERY_TOKEN`) and attaches it to the singleton `DatabaseProvider` (`RemoteBaseSource`; null when no peers ⇒ pure-local path byte-identical). The `get_base_snapshot_symbols` tool pages a base snapshot by identity hash: local-complete → `LocalBaseSnapshotSource` (`origin=local`); else remote peer (`origin=remote`) — but ONLY after the fail-closed `TryBeginRead` gate, so a remote fetch can never widen local authorization (the peer independently authorizes the presented token). Provenance stamps `origin`/`base_identity_hash`; the wire format is `SnapshotWireJson.Options` (byte-identical to the service's `ServiceJson.Options`). The tool is **LOCAL-ONLY** — it is deliberately EXCLUDED from the multi-tenant `ServiceApp.RemoteQueryTools` allowlist because its caller-supplied `identity_hash` is NOT bound to the repository scope `TryBeginRead` authorizes; cross-service snapshot federation on the service surface goes through the per-hash-authorized `/query/snapshots/{identityHash}/symbols` HTTP endpoint instead (`RemoteToolAllowlistTests` guards this). Multi-peer paging stays deterministic: each peer gets its OWN `SnapshotPageCache` (the cursor is a peer-local `symbols.id`), and `CompositeBaseSnapshotSource` skips a peer that DEFINITIVELY lacks the snapshot (a 404) on any page, skips a merely UNREACHABLE peer only on the first page (a resumed cursor is never failed over into another peer's id-space), and lets a real 5xx propagate. The `DatabaseProvider` singleton is registered via a DI FACTORY so the container disposes the owned `HttpClient` on shutdown.
- **Provider-snapshot growth is immutable (issue #53):** a provider that gains a project after publish must produce a NEW pending provider generation + republish, NEVER mutate a complete one; `MarkComplete` is a guarded no-op on an already-complete snapshot (same immutability contract as Phase 9/10/12).
- **Service re-select of a superseded snapshot (issue #85).** A branch advance supersedes the previous head, so a reset/force-push A@10 → B@20 → A@30 leaves A `superseded`. A **sequence-bearing** service ensure of A re-selects it on the no-worker reuse path, mirroring `IndexOrchestrator.SelectExistingSnapshot`. In ONE raw `BEGIN IMMEDIATE` transaction under `_writeGate` (`WithWrite` is not reentrant, so never nest it) it restores A to `complete` and then runs the #84 forward-only `AdvanceBranchPointerForwardOnly`. A higher sequence re-points the branch; a lower/equal one declines the pointer move but leaves A `complete` (parity with the orchestrator). The job verdict comes from A's durable coverage row, which is read but never written. This happens ONLY when `SnapshotStore.IsReselectable` holds: superseded + published (`published_at` set) + non-overlay + still owns mapped project data + every provider still published. The `index_runs` ledger is deliberately not consulted, because `run_id` is bound at first staging and a retry republishes into the same id. Otherwise A is demoted to `failed` and the worker rebuilds it into the same id, so a data-less snapshot is never resurrected. The null-sequence path is unchanged (it still goes to the worker). The terminal-attach fast path validates the job's snapshot and advances the branch in ONE write-gate hold. Never release the gate between the usability check and the advance: a concurrent ensure could supersede the snapshot in that window, leaving the head on a `superseded` snapshot.
- **Service ensure production outlives its caller (issue #148).** `SnapshotService.EnsureSnapshotAsync` runs every ensure as a SERVICE-OWNED operation bound to the service lifetime (`_lifetime`, cancelled only by `StopProduction` — wired to host `ApplicationStopping` — or `Dispose`); the caller's token (HTTP `RequestAborted`) only bounds ITS OWN wait (`WaitForCallerAsync` → `WaitAsync(ct)`), so a client disconnect/timeout never cancels or requeues the worker: the job stays `running` and publishes normally. **Never pass a request token to `_worker.ProduceAsync` or `_writeGate.WaitAsync` on the production path.** Productions are tracked in an in-flight registry keyed by identity hash (`_inFlight`, guarded by `_inFlightLock`, which is never held while WAITING for the write gate: a write turn is only QUEUED under it, #158); an ensure of an identity already producing attaches WITHOUT the gate (the worker runs once; its `wait=false` answer is immediate), and a non-owner that sees a terminal result re-runs the terminal-attach path on its own turn so ITS branch pointer is advanced (#84/#85 unchanged). The production deregisters itself BEFORE releasing the gate, so no request that can see the new durable state attaches to a finished production.
